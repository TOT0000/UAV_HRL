========== COMMON ==========

You design additional state features and fixed reward weights for centralized TD3 movement control in the UAV data-collection system below.

1. System operation and objective

The system contains 16 UAVs, one ground station (GS), and 2–8 regions of interest (RoIs) in a standard 1000 × 1000 m disaster area.

UAV tasks are:
- Search: discover previously unknown RoIs.
- Visual sensing (VS): capture data from an assigned RoI.
- Communication collection (COM): receive data from an assigned ground source (SR).
- Hover: remain hovering.

A UAV may serve VS and COM simultaneously with different targets.

The system has three control functions:
- Task allocation assigns UAV roles and service targets.
- TD3 controls movement for UAVs identified by movement_mask. Each controlled UAV has speed, horizontal-heading, and vertical-speed action components. Existing controllers handle search and hovering.
- After movement updates positions and links, the routing controller selects packet next hops during communication slots.

A movement decision occurs every 1 s. Each interval contains four communication slots of 0.25 s. An episode lasts 60 s.

The sequence is:
current observations and task assignments
→ TD3 movement action
→ position and sensing/link updates
→ data acquisition, queueing, uploads, and relay transmissions
→ interval delivery, energy, and penalty calculation
→ next movement decision.

Task allocation changes when its existing update rules trigger. TD3 changes positions; task assignments, next hops, and scheduling are controlled by existing mechanisms.

Data paths:
VS: capturing UAV → zero or more relay UAVs → GS.
COM: SR queue → serving UAV → zero or more relay UAVs → GS.

Packet deadlines are measured from generation until GS delivery:
- VS: 2.5 s.
- COM: 2.0 s.

Moving a packet to another UAV does not restart its deadline.

The primary objective is episode energy efficiency:

EE = sum_t B_timely,t / sum_t E_movement,t

B_timely,t is useful data delivered to the GS within its deadline.
E_movement,t is movement energy of all UAVs.

Acquisition and intermediate forwarding contribute to the task when the data subsequently reaches the GS on time.

The system also tracks end-to-end deadline violations. Interpret these together with useful delivery volume and energy use.

6. Training and evaluation

The host checks the candidate interface, executable behavior, and numeric validity.

Each valid, nonduplicate candidate is trained independently from scratch for {{TRAIN_EPISODES}} episodes using consistent training settings and the same training scenario sequence.

Training retains the existing lambda update procedure.

The checkpoint at episode {{TRAIN_EPISODES}} is evaluated on the same {{EVALUATION_EPISODES}} fixed scenarios:
- {{EVALUATION_ROI_COUNT}} RoIs.
- {{EVALUATION_AREA_SPEC}}.
- {{EPISODE_SECONDS}} seconds per episode.
- Exploration and learning updates disabled during evaluation.

For evaluation episode i:

EE_i = sum_t B_timely_i,t / sum_t E_movement_i,t

The candidate score is:

mean_EE = (1/N) * sum_i EE_i

N is the number of evaluation episodes. This is the arithmetic mean of the
per-episode EE values; it is not total delivery across all episodes divided by
total energy across all episodes.

Candidates are compared by mean evaluation EE, including comparison with the original method at the same training budget.

Timely useful delivery, movement energy, and deadline violations help interpret the results.

The candidate with the highest historical mean evaluation EE is the reference for the next round. Completed candidates are represented in the feedback through recent detailed results or historical summaries.

7. Design guidance

Connect the task to the environment:
- Identify relevant UAVs, service targets, queues, and links.
- Determine how TD3 movement affects data acquisition, timely delivery, and movement energy.
- Select corresponding observations with appropriate units and validity conditions.

Translate the objective into design considerations:
- Deliver useful data to the GS within its deadline.
- Balance movement energy against useful delivery.
- Coordinate sensing and source uploads with subsequent relay service.

Use these relationships to choose feature formulas and weights.

Each feature description should make its meaning, normalization, and reward direction checkable against the implementation.

Summarize the necessary design rationale in design_summary and feature descriptions. Keep the code consistent with those descriptions.
