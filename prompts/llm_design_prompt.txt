Design additional state features and their reward weights for the UAV post-disaster data collection task below. These features will help a centralized TD3 agent learn movement control.

1. Task and objectives

A fleet of 16 UAVs operates in a standard 1000 x 1000 m area. Each episode contains 2 to 8 regions of interest (RoIs) and lasts 60 seconds. UAVs discover RoIs, acquire visual sensing (VS) data and communication (COM) data from ground sources (SRs), and deliver the data to a ground station (GS) through a UAV relay network.

The objectives are to improve energy efficiency and reduce end-to-end deadline violations:

Energy efficiency = total useful data delivered to the GS within its deadlines / total movement energy of all UAVs.

VS data generation depends on valid sensing geometry; its useful amount depends on RoI coverage and image quality at capture time. COM data is uploaded from an SR to its serving UAV. Both types may wait in queues and traverse multiple relay hops. Collection is credited when useful data reaches the GS within its deadline.

VS and COM deadlines are 2.5 seconds and 2.0 seconds, respectively, measured from data generation through source-side waiting and subsequent transmissions.

Interpret queue load and deadline pressure in the context of task service: low backlog or few violations can also result from acquiring less data.

2. TD3 control scope

An existing task allocator determines UAV tasks and service targets, and a routing controller selects packet next hops. TD3 controls movement for the VS/COM UAVs identified by the movement mask. Search UAVs follow the existing search controller, while hovering UAVs remain hovering.

TD3 acts once per second. Each movement interval contains four communication slots of 0.25 seconds. Each UAV has three action components - speed, horizontal heading, and vertical speed - for 48 joint action dimensions.

A UAV may simultaneously serve VS and COM tasks with different targets. Movement affects sensing quality, SR uploads, UAV backhaul connectivity and capacity, queue service, and energy consumption. Design features that help the policy recognize these relationships.

Assign each feature a fixed reward_weight w_k satisfying:

sum_k abs(w_k) <= 1

Positive weights reward larger feature values; negative weights penalize them. A zero weight keeps the feature in the state without directly contributing to reward.

The host program uses the same feature values to compute:

s_aug = concat(s_original, f)
r_extra = sum_k w_k * f_k
r_total = r_base + beta * r_extra
