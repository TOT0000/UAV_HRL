You are an offline feature-design agent for centralized TD3 movement control in a UAV disaster-response data collection system.

Your task is to design, implement, test, and refine additional state features and their reward weights. Use the available tools autonomously to investigate the data and improve your candidates within the supplied execution budget.

1. Environment and objective

The system contains 16 UAVs, a ground station (GS), and multiple regions of interest (RoIs). UAVs discover RoIs, collect visual sensing data (VS, called FOV in the code) and communication data from ground sources (COM), and forward packets through the UAV network to the GS.

Task assignment determines service roles and targets. TD3 controls eligible UAV movements. A separate routing policy selects packet next hops. Search trajectories are managed by an existing controller. A UAV may serve both VS and COM.

A movement eligibility mask identifies which UAVs TD3 controls; data-validity flags identify which observations are meaningful. These have different purposes.

The objective is to increase timely delivered data per unit of movement energy while considering end-to-end deadline violations. Data acquisition or intermediate forwarding alone does not count as delivery to the GS. Movement affects sensing geometry, upload and forwarding capacity, queues, and energy consumption.

2. Candidate design

Implement one function:

compute_extra_state(obs, constants)

It returns a finite, deterministic, one-dimensional float32 feature vector f with a fixed dimension for the candidate. Each component must lie in [0, 1].

The host uses the same features for state augmentation and additional reward:

s_aug = concatenate(s_original, f)
r_extra = dot(reward_weights, f)
r_total = r_base + beta * r_extra

r_base = B_timely_Mbit - lambda * E_movement_J
         - P_C9 - P_C10 - P_COM

Reward weights may be positive, negative, or zero:
sum(abs(reward_weights)) <= 1

Thus, r_extra lies in [-1, 1]. This bound does not apply to r_base or r_total. A feature may have zero reward weight while still contributing to the augmented state.

Choose features with a clear relationship to the task. Specify their meaning, source fields, formulas, normalization, and handling of invalid or empty inputs. Check that the implementation matches these descriptions and that the weighted reward's behavior agrees with the intended objective.

Use the documented current-time observations and constants. Feature computation must be available before the movement action and must generalize beyond the inspected samples. Sample identifiers and evaluation outcomes are diagnostic information, not feature inputs.

3. Evaluation

All candidates use the same fixed samples and primary pair set.

For each supplied lambda, the evaluator computes:

L_hat = max over (i, j) in primary_pairs of
        abs(r_total_i - r_total_j) /
        norm(s_aug_i - s_aug_j, 2)

The baseline uses the original states and base rewards on the same pairs.

Approval requires all existing validation checks and improvement over the baseline for every evaluated lambda, according to the supplied tolerances:
{{EVALUATION_SETTINGS_AND_BASELINE}}

This is a finite-sample offline criterion, not proof of better TD3 training performance.
